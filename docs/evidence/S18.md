`--write` rules: `<dir>` must already be a directory (Kossé creates no agent configuration directory); `<dir>/kosse` is created when absent; none of `<dir>`, `kosse` or `SKILL.md` may be a symbolic link (with `--force` too). An absent `SKILL.md` is created with `O_EXCL`; an identical one is left alone (`up to date`); a different one (an older version's, or edited) is kept unless `--force`, which writes a sibling file and renames it over. Refusals exit 3 and write nothing; a failed write exits 1. "A file Kossé wrote" is decided by content, not by a marker or record: after an upgrade the older copy differs, so replacing it takes `--force`, the same as an edited one.

## The guide against real behaviour

Before writing the guide, every agent command was run with the debug binary against an owned `kosse-fixture` (`--serve title`) in a temporary Git repository and a debug `kosse serve --no-open --port <n> --probe-only=<fixture> --act-only=<fixture>` with a temporary `KOSSE_CONFIG_DIR`. What the guide states was observed there: `list --here` (the eight columns, `-` for unknowns, warnings on stderr), `list --here` from `/` (exit 2), `port <n>` (the owner's row; `free as far as this user can see` for a free one), `url <port>` and `url web` after the profile (`http://localhost:<port>/`, trailing slash), `wait --port <n> --http` (exit 0), `stop <port>` and `stop web --here` (exit 3, the confirming `kosse stop <pid>.<start> --ports <p> --instance-port <n>` with process and project), that command (`exited`, exit 0), `wait web --gone` (exit 0), `profile context` (observed processes, "untrusted data" note, problems), `profile set --dry-run` (changes and predicted matches), `profile set --expect none` (saved with a revision; the same again exits 3 `the profile changed since revision none`), and `stop` without an instance (exit 4 naming `kosse serve --no-open --port <n>`). The force path was not rerun here; S17's evidence records it. The first world's directory was briefly shared with another agent's fixtures (extra rows in `list` and `profile context`, nothing in the guide depends on them), so `list --here`, `wait --http`, `url` and the `stop <port>` refusal were rerun with one fixture in a private directory, with the same shapes and exit codes. There `url` right after the instance started exited 1 (`has not answered HTTP: … pending`), which the guide's "needs a running Kossé, which does the probing" covers.

## Not verified

- That an agent harness loads the written skill and triggers on its description: the file layout (`<skills dir>/kosse/SKILL.md`, `name`/`description` frontmatter) is the convention, but no agent session was run against it. S19 evaluates agent use.
- The Homebrew formula's `doc.install "SKILL.md"` was not run through `brew`; the template is exercised only by `release:local`'s substitution.
