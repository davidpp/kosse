# S11 evidence: the real window, driven and fixed

Recorded 2026-10-28 on macOS 26.6.2, Apple silicon, Rust 1.99.1, Bun 1.4.2, Playwright 1.64.1, on the S11 tree (parent `0b3f6aa`), before commit. The review round's fixes are listed under [Review fixes](#review-fixes); which commands ran on which tree is stated there.

The owner used the real app and hit defects no test caught, because Playwright drives its own WebKit build at desktop sizes, never Kossé's window. This slice adds a way to drive the shipped window ([docs/agent-drive.md](../agent-drive.md)), uses it to find the causes, and keeps them fixed with a suite that runs in that window.

## Bugs found in the real window, and their causes

1. **Every modal was a 2px sliver behind a visible backdrop** (Stop, Force, Customize and its removal confirmation; the Inspect sheet was fine). Reproduced through `eval` on the first try: `dialog.open === true`, `display: block`, opacity 1, rect `512×2`, margins `389px` (centred), its column `height: 0`. Cause: the modal is sized by its content (UA `height: fit-content`), and the inner column had `max-h-[inherit]`, inheriting the UA's `max-height: calc(100% - 2em - 6px)`. macOS 26's system WebKit resolves that percentage against the dialog's indefinite height as 0 (a `-34px` cap), so the content collapsed to the dialog's 2px of border; Playwright's WebKit 2370 treats it as `none`. A first fix (`open:flex` + `flex-1` columns) collapsed the same way: `flex-basis: 0%` hit the same resolution. Fix (`web/src/components/dialog.tsx`, `customize-dialog.tsx`): nothing inside the modal sizes itself from the dialog's height; the column caps itself at `100dvh - 2rem - 2px`, the Customize form and body use `flex-auto`. The sheet keeps its definite `h-dvh`.
   - Before / after in the window (the "before" re-applies the old rule through CSSOM, so it is the same build): [stop-dialog-before.png](../screenshots/window/stop-dialog-before.png), [stop-dialog-after.png](../screenshots/window/stop-dialog-after.png); Force at the minimum size, light: [force-confirm-min-light.png](../screenshots/window/force-confirm-min-light.png).
2. **Rows overflowed horizontally.** With All listeners on, `scrollWidth` was 815 px at 780 and 800 px wide (18 elements past the edge: the metrics + Inspect/Stop cell). Cause: from `md` (768 px) the row is a three-column grid whose last column is `auto`, and that cell was `md:flex-nowrap`, so its max-content width (`up 20d 11h · cpu warming up · mem …` plus two buttons) pushed the grid past the window. Fix (`project-card.tsx`): the cell wraps at every width (still one line whenever it fits). On this machine the default 1180×780 did not overflow; the owner's report at the default size is consistent with the same cell carrying wider real values, but that exact state was not reproduced.
3. **Kossé's own row offered Stop**, which `revalidate` then refused. The snapshot now carries `instancePid` (the publishing process; `#[serde(default)]`, so no schema bump), the dashboard shows "this Kossé" with a disabled Stop and the reason (title and screen-reader text), a deep link to it says "Kossé cannot stop itself" with nothing to confirm, and the tray omits Stop… for it (`menu::tests::kosse_itself_has_no_stop`).
4. **The window's Dock/⌘-Tab icon was the generic "exec" icon**: the window process now sets `NSApplication.applicationIconImage` from an embedded 512 px PNG (11,897 B release, 16,350 B preview). The tray process is an accessory app with no Dock icon, so it sets none.

Sweep with no defect found: search (`/` then typing), All listeners, Open (captured, the window stays on `/`), Inspect, Try HTTP, Stop → still running → Force, respawn report, Customize save and remove, `j`/`k`/Enter/Escape, deep links through `POST /api/window` (the tray's Inspect/Stop… path), light and dark. One harness finding, not a product bug: WebKit queues key and mouse events separately, so a click sent microseconds after typed keys can land first (a person cannot type and click that fast; pressing Enter after typing saved the full value). The suite waits for the field's value.

## App identity now, and whether a bundle is justified

What a bare executable gets: the window's Dock and ⌘-Tab tile is now Kossé's (release) or the preview tile (debug), set at runtime right after the window process starts. The **name** stays `kosse` (lowercase) everywhere macOS reads it from a bundle: ⌘-Tab, the window's bold app menu, Activity Monitor (two `kosse` processes: the app and its window), Force Quit, and `NSRunningApplication.localizedName` (`"kosse"`, observed through `status`). Not verified by eye here: the Dock tile itself and the menu-bar glyph (no screen capture without a permission prompt); they are human checklist items (S08 step 11).

A minimal `Kossé.app` (`Info.plist` with `CFBundleName`/`CFBundleDisplayName` "Kossé", `CFBundleIdentifier` `com.davidpp.kosse`, `CFBundleIconFile` `Kosse.icns`, `LSUIElement` for the tray process) would fix the name everywhere and give the icon before the first frame. Remaining gaps it closes: the name only, plus a stable bundle identity, which only matters once notifications, signing/notarization or per-app permissions arrive. Cost: `release:local` assembles and ad-hoc signs a bundle; `install:local`/`uninstall:local` and their records cover `<prefix>/Applications/Kossé.app` plus a `bin/kosse` symlink into it; the launch agent and `doctor` name the bundle's executable; the window child must be the bundle's executable to inherit its name; the Homebrew formula becomes a cask or installs the app beside the keg. The `curl | tar` story keeps working (no quarantine through curl), but "one file you can copy" becomes "a folder plus a symlink". Recommendation: not yet. The icon was the visible gap and is fixed; a lowercase `kosse` in ⌘-Tab is cosmetic. Do the bundle together with signing and notarization, which need one anyway.

## Review fixes

After the two review lenses (quality, docs):

- Control socket: 5 s read/write timeouts, a request capped at 1 MiB, back-off on accept errors (giving up after 50 in a row, so `EMFILE` cannot spin), the socket removed when the window closes (`LoopDestroyed`), and `quit` answered before the window closes. Snapshots go only to an absolute `.png` path under `KOSSE_WINDOW_CONTROL_DIR` (`var/app`) or the temporary directory, never over a non-regular file and opened with `O_NOFOLLOW` (`rustix` gains its `fs` feature); `bun run app -- shot --out` copies from `var/app`.
- Dialog caps agree: the dialog itself is `max-h-[calc(100dvh-2rem)] overflow-hidden`, the column 2px less (its border), so no nested 2px scroll at 560×420. `test:window` now also requires that the dialog box itself does not scroll (`scrollHeight <= clientHeight`).
- `bun run app`: the session records the app's PID and `ps` start time, and `stop` releases an app orphaned by a dead host only when PID, start time and executable match; a `start` timeout stops the host it spawned; the opener script takes its log path from `KOSSE_APP_OPENED` (no checkout path interpolated into shell); `status` lists each fixture's `startedAtSecs` for `show inspect:<pid>.<start>`; clearer no-session message; `Backspace` in the usage.
- `build.rs` watches only `.git/HEAD` (or a worktree's `.git` pointer and its `HEAD`), not the whole `.git` directory.
- Vitest: `web/src/components/kosse-itself.test.tsx` renders Kossé's own row (disabled Stop, "this Kossé", the reason in `title`; another row keeps Stop) and the "Kossé cannot stop itself" deep-link dialog (jsdom has no modal dialogs, so that file supplies `showModal`/`close`; real dialogs are `test:window`'s).
- **Test window mode changed from `offscreen` to `transparent`.** Asserting the window's position (review item 6) showed that an offscreen titled window does not stay off-screen: after a resize, and in one run already at creation, AppKit moved it to `[240, 33]` on the main display, so earlier `test:window` runs may have shown it on the desktop. Hiding it and restoring the position around a resize, or `setFrame:display:`, did not prevent that; a borderless offscreen window stayed put but WebKit then treated the page as hidden. `KOSSE_TEST_WINDOW=transparent` keeps the window on screen at 1% opacity, at the floating level and click-through (`ignoresMouseEvents`), with no Dock icon or activation: the control socket's `NSEvent`s still go to the window directly. `test:window` asserts the opacity stays below 2% throughout.
- **Blocked: the screen was locked** (`ioreg`: `CGSSessionScreenIsLocked=Yes`) during this round. A locked screen occludes every window (`status` reports `"occluded": true`; even a normal visible `bun run app` window answered no evaluation), so neither the transparent mode nor the 2px-scroll fix could be judged in the real window. `test:window` and `app start` now refuse to run on a locked screen with that reason. Last run before the refusal was added, while locked: 59 passed, 2 failed (the window counted as occluded; Remove profile timed out under the throttling). **To do on an unlocked screen:** `bun run test:window` (expect all checks green, including "shown but transparent and click-through"), then confirm by eye that nothing appears while it runs.
- Docs: README Development block and the blueprint command contract list `app` and `test:window`; AGENTS.md and CONTRIBUTING.md say CI is configured to run it, first run pending.
- After these fixes: `bun run check` exit 0 (214 nextest tests, 39 web tests, bundle 49.48 kB); `bun run test:e2e` 28 passed, 2 skipped; release `kosse` 5,830,224 B with no debug strings.
