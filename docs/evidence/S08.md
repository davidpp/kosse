# S08 evidence: menu-bar app, dashboard window, `kosse open` and single instance

Recorded 2026-10-28 on macOS 26.6.2 (25G83), Apple M4 Pro, arm64, Rust 1.99.1, Bun 1.4.2. The tree is S08 rebased onto `0c015a5` (S07, the dashboard), including the fixes from a two-lens review; the commit that adds this version of the file is its fingerprint. `web/` changes only in the generated `contracts.ts`.

## Decisions

- **A second launch refocuses, never duplicates** (product decision after review). `kosse` and `kosse open` against the menu-bar app fetch the session token (`Host` only) and send a same-origin `POST /api/window`; the app shows its one window at the route and exits nothing. Against `serve` (headless) or another `open` (ephemeral) there is no window to show: `open`, and `kosse` for `serve`, open the browser with the reason; `kosse` refuses an ephemeral holder (exit 1) because it would vanish with its window. There is no detached window.
- **Contract change:** `Health.mode` (`resident | ephemeral | headless`), `WindowRequest`/`WindowRoute`, `ApiErrorCode::notResident`. `contracts.ts` is regenerated (`bun run contracts`); S07 conflicts there are regenerate-only.
- **Owner first.** `instance::find` looks up the processes listening on `127.0.0.1:<port>` (and the wildcard) through `kosse_core::sockets` and their effective UID through `kosse_core::inspect::vitals`, before any HTTP request. None visible (another user's sockets are invisible without administrator rights), an unreadable owner, or another UID: `… is held by another user's process …`, exit 1. No request, so no token, ever goes to another user's instance.
- **Window owned through stdin.** End of stdin closes it, so it never outlives the app, `open`, or a test, even on SIGKILL of the owner (tested). Each request is acknowledged (`shown <url>`); a route sent while the user was closing the window is shown again in a new one. The reader thread reaps the child as soon as it exits.
- **Main-thread loop:** tao 0.37 runs on the main thread; tray-icon's status item is created at `StartCause::Init` as its docs require. The instance runs on the multi-threaded tokio runtime that the closure keeps alive; `ControlFlow::ExitWithCode` is set only after the server drained and the scanner stopped (tao exits the process from `run`). `/usr/bin/open` is spawned, never waited for, on the main threads.
- **Activation (macOS 14+ is cooperative):** after a menu click the tray calls `yieldActivationToApplication` + `activateWithOptions` on the window process; the window calls `NSApplication.activate` when told to show a route. A request from a terminal (`kosse`, `kosse open`) comes while the terminal is the active app, so macOS may keep the window behind it; checklist step 8 records the result.
- **Cheap rebuilds:** a tokio task compares models and sends only changes (plus a 5 s tick for the stall rule). In the measurement run below (131 s, 30 fixtures plus this machine's own changing listeners), the menu was rendered 15 times.
- **Attention icon** only for scanner failure (with or without a last good observation) or no finished scan for 3 intervals (9 s); never for a probe result. The reason is the first menu line and the tooltip. A window fallback adds a separate one-shot line (`Dashboard window unavailable: … (opened in the browser)`) until the next click.
- **Icon sizing:** tray-icon scales any image taller than 22 pt down to 22 pt, so the 36 px @2x glyph is centred on a 44 px transparent canvas: 18 pt glyph, Retina pixels, template (black + alpha) so macOS tints it.
- **Untrusted text** in menu labels passes `printable` (control/bidi escaped) and `&` is doubled (muda mnemonics).
- **No `.app` bundle needed so far; pending the human checklist.** The status item and the web view start from the bare binary in every automated run. Without a bundle the window's Dock icon is the generic executable icon and macOS names the app menu after the process; `brand/Kosse.icns` stays unused unless a bundle turns out to be needed.
- **Test hooks are debug-only** (compiled out of release): `KOSSE_TEST_WINDOW=headless|headless-once|fail`, `KOSSE_TEST_OPENER`, `KOSSE_TEST_TRAY`. A headless window also reports, after each load, the heading of the dashboard dialog that opened (`dialog "<heading>"`, or `dialog null` after 5 s; a page script polled by wall clock, since WebKit throttles timers in hidden windows), so tests see what a deep link did. They keep windows and browsers off the developer's desktop; the window, web view and tray code under test is the shipped code.

  - `a_second_launch_refocuses_the_menu_bar_app_without_a_second_window_or_scanner`: against the app, `kosse --no-open --port <p>` prints only `kosse: Kossé 0.1.0 is already running at <url>`; `kosse --port <p>` prints `kosse: Kossé 0.1.0 is already running at <url>; showing its window` and the app's window loads `/`; `kosse open --port <p>` prints `kosse: showing the window of the Kossé menu-bar app at <url>` and the **same** window child reloads.   - `the_window_endpoint_is_guarded_and_routes_to_the_one_window`: `POST /api/window` without the token or with a foreign `Origin` is `403`, an invalid route `400`, and none shows anything; the accepted request is `204` and loads `/?inspect=4242.1761000000`; a second one within a second is `429`; `serve` answers `409 notResident`.
  - `a_second_launch_never_duplicates_a_headless_or_ephemeral_instance`: with `serve` on the port, `kosse --no-open` prints ``kosse: `kosse serve` is already running at <url> (no menu-bar app)``, while `kosse` and `kosse open` print the reason plus `; opening <url> in the default browser` and the opener gets the URL.   - `a_killed_owner_takes_its_window_with_it`: SIGKILL of a `kosse open` (the test's own child); its window process is gone within 5 s.
  - `the_trays_window_fallback_opens_the_browser_and_says_why_in_the_menu`: with the window failing, Open Dashboard hands the URL to the opener, the next menu starts with `Dashboard window unavailable: the dashboard window did not start (disabled by KOSSE_TEST_WINDOW=fail) (opened in the browser)`, and stderr carries the reason exactly once (the window child adds no line).
  - `an_unrelated_port_occupant_is_never_trusted` (an HTTP-200 and a banner fixture: `kosse` and `kosse open` exit 1 with `kosse: 127.0.0.1:<port> is in use by a process that is not Kossé; stop it or choose another port with --port`; `list` is a one-shot), `open_serves_until_its_window_closes_then_leaves_nothing_running`, `a_window_that_cannot_start_falls_back_to_the_browser_with_the_reason` (serving until SIGTERM, then exit 0 and port released), `headless_serve_has_no_tray`, `the_menu_bar_app_stops_cleanly_on_sigterm`, `a_crashed_window_leaves_the_scanner_running_and_is_replaced` (SIGKILL of the app's own window child, confirmed by parent and command line: revisions keep advancing, the next Open Dashboard spawns a new child that loads).

## Measurements (Footprint gate)

One run of S03/S04's harness, all rows from it. Release profile with `CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS=true` (optimized; needed for `--probe-only` and the headless window hook, as in S04); 30 owned banner fixtures in 10 worktrees, probing only them; per row a 5 s settle, then 60 s of `ps` cputime and RSS, then `footprint` (physical footprint: private dirty memory, what Activity Monitor calls Memory). The window is the headless test window: a real WKWebView with the dashboard loaded, but invisible, so WebKit may throttle rendering; the visible-window cost is a checklist item.

| Process                                | CPU in 60 s     | RSS (ps) | Footprint             |
| -------------------------------------- | --------------- | -------- | --------------------- |
| `serve` (baseline)                     | 0.16 s (0.27 %) | 14.7 MiB | 5.2 MB                |
| `kosse` app, window closed             | 0.21 s (0.35 %) | 47.9 MiB | 12 MB                 |
| `kosse` app, window open: app          | 0.18 s          | 49.6 MiB | 14 MB                 |
| window open: `kosse window` child      | 0.01 s          | 91.5 MiB | 22 MB                 |
| window open: its 3 WebKit XPC services | 0 s             | 86.8 MiB | 44 MB (12 + 5.2 + 27) |

- The tray costs no measurable CPU over `serve` (within noise). Its memory cost is about **7 MB** of private footprint, almost all of it `MALLOC_SMALL` (7.3 MB dirty in the app's `footprint` breakdown, against `serve`'s total of 5.2 MB): AppKit's per-process state once `NSApplication` and the status bar exist. No cheap trim was found; it is the price of a native status item. RSS also counts shared AppKit pages, so it overstates the cost.
- An open window costs about 66 MB of footprint across its own process and WebKit's services; closing it ends the process and its services (checked after quit: no window process left), which is why it is a child.

## Human checklist (for the Kabane human task)

On a desktop session, from the repository root, with S07 merged:

1. `bun run build && cargo build --release -p kosse-fixtures`.
2. Start an owned HTTP fixture in a Git project:

   ```sh
   F="$PWD/target/release/kosse-fixture"
   mkdir -p /tmp/kosse-check/shop && git -C /tmp/kosse-check/shop init -q -b main
   (cd /tmp/kosse-check/shop && sleep 1800 | "$F" --listen 127.0.0.1 --serve title --max-lifetime-secs 1800 &)
   ```

   Note the port in `listeners` of the line it prints.

3. `target/release/kosse`. Expect: the Kossé glyph in the menu bar, tinted like neighbouring icons in a **light** and a **dark** menu bar (toggle Appearance), crisp at 18 pt; no Dock icon for the app; the dashboard window titled "Kossé" opens and comes to the front.
4. Click the icon: a `shop — main` section header, then `shop :<port>` (submenu Open / Inspect / Stop…), then Other Listeners, Open Dashboard, Quit Kossé. Within 15 s, Open appears for the fixture.
5. Open → the fixture's page in the default browser. Inspect → the same window (not a second one) shows that service's details, titled "Kossé — shop", and comes to the front.
6. Stop… → the dashboard's Stop confirmation for that process (PID, project, every port); cancel it. Then confirm it once: the fixture exits. Restart it with step 2.
7. Open Dashboard with the window minimised or behind another app: it comes forward. Close it (⌘W), then Open Dashboard: a new window opens. ⌘C/⌘V work in the dashboard's search field.
8. In a terminal, with the app running: `target/release/kosse` → `kosse: Kossé 0.1.0 is already running at http://127.0.0.1:47831/; showing its window`; the **same** window shows the dashboard, still one menu-bar icon, no second window. Record whether it came to the front or stayed behind the terminal (macOS 14+ cooperative activation may keep it behind; that is the expected platform limit, not a failure). `target/release/kosse open` → `kosse: showing the window of the Kossé menu-bar app at http://127.0.0.1:47831/`, same window. `target/release/kosse list --json | jq .scanner.intervalMs` → `3000`.
9. Quit Kossé → icon and window disappear; the fixture is still listening: `lsof -nP -iTCP:<port> -sTCP:LISTEN` shows it.
10. `target/release/kosse open` (no app running) → a window; close it → the command prints `kosse stopped` and returns, and `lsof -nP -iTCP:47831 -sTCP:LISTEN` is empty.
11. Clean up: end the `sleep` of step 2 (the fixture exits on EOF), `rm -rf /tmp/kosse-check`.
