## Decisions

- **Git via the CLI, not gix.**
  - Git's own discovery covers directory and file `.git` (linked worktrees, submodules, `--separate-git-dir`) and both ref backends. Reading `HEAD` directly would be wrong for reftable repositories, whose `HEAD` file is a stub.
  - No new dependency; `gix` would add dozens of crates to the shipped graph for three answers per worktree.
  - Cost: one `rev-parse` per worktree per 60 s, one `symbolic-ref` per 15 s (plus `rev-parse --short` when detached). The developer-directory binary takes about 3 ms, against about 8 ms through `/usr/bin/git`.
  - `/usr/bin/git` is never run: without the Command Line Tools that shim opens an install dialog. `git` is located through `xcode-select -p`; if it is absent, worktree services get `attributionUnavailable {reason: gitUnavailable}`, and the lookup is retried after 60 s (tools may be installed meanwhile).
  - `git` runs only for directories where the walk found a `.git` entry, so non-Git working directories cost no subprocess.
- **Bounded time.**
  - Each command: 2 s, after which our own child is killed. Stdout is drained on a helper thread, so large output cannot block the child into a false timeout, and a grandchild that inherited the pipe cannot hold the read past the deadline.
  - Each scan: new `git` commands may start only during a 1 s budget (`GIT_BUDGET`). After that, stale cache entries are reused as they are and unresolved worktrees are reported as `attributionUnavailable {reason: deferred}`; deferrals are not cached, so the next scan resolves them.
  - The stat-only walk has no deadline. A working directory on a stalled network mount blocks the scan, and readers see the snapshot age grow. Moving walks to helper threads would leak one blocked thread per stalled path, so I kept it inline and documented it.
  - `serve` shutdown waits at most 3 s for a scan in progress, then exits anyway. `refresh()` returns within 10 s (`REFRESH_TIMEOUT`). Requests are coalesced, not rate-limited, so S04's HTTP refresh endpoint should rate-limit callers.
- **Walk boundaries.** The walk stops before the user's home directory (a dotfiles repository in `~` never claims projects below it), before `/`, and at a device change. `git` gets `GIT_CEILING_DIRECTORIES` set to the candidate root's parent, so it cannot look further up than the walk did. Outside Git, the nearest manifest directory is the project. With neither, there is no project and no warning. An unresolvable cwd (for example, deleted) is `attributionUnavailable {reason: cwdUnavailable}`, never a guess.
- **Identity.** `Project.root` is the canonical worktree root (`fs::canonicalize` returns the on-disk Unicode form). `git`'s toplevel must canonicalize to the same path, or the result is refused as `gitFailed`. Worktrees sharing a common directory stay separate projects; `commonDir` and `repositoryName` are exposed for display grouping only. Git output with a newline inside a path yields extra lines and is refused rather than misparsed.
- **Package label.** The nearest directory within the project holding one of 12 manifest names, given as a relative path, directory name and manifest list. Manifest contents are not read. Outside Git, each manifest directory is its own project: a non-Git monorepo is not grouped (deferred to S06 profiles).
- **CPU.**
  - `sysinfo` 0.39.6's `cpu_usage` is unusable for a selective refresh on macOS. Its interval is the time since the last refresh of _any_ process (`get_time_interval` in `src/unix/apple/macos/system.rs`), and it keeps the previous value when a process used no CPU in the window (`compute_cpu_usage` in `src/unix/apple/macos/process.rs`, `if total_time_diff > 0`).
  - `metrics.rs` keeps its own baseline per identity, `(accumulated CPU ms, Instant)`. A window shorter than 250 ms repeats the last figure and keeps the older baseline.
  - Memory 0 means the task-info read failed (other users' processes): CPU and memory are then `unavailable` and listed in `metadataUnavailable`.
- **Pruning.** A selective `sysinfo` refresh never drops PIDs it was not asked about, so the table would grow with every process that ever listened. The inspector rebuilds it before a refresh whenever it holds a PID outside the current set. CPU baselines and attribution caches likewise keep only what the current scan used.
- **Snapshot shape (contract v2).**
  - The blueprint's "last successful observation" is an explicit nullable `observation`. A first scan that fails publishes `observation: null` with `scanner.failure`, never an empty success.
  - `revision` counts publications, failures included. `instance` (opaque, new per process) lets clients tell a restart from an out-of-order event.
  - Staleness: a failing scanner republishes the last good observation with `failure` set; a hung one publishes nothing, so readers compare `observation.scannedAtMs` with `scanner.intervalMs`.
  - `SNAPSHOT_SCHEMA_VERSION` is 2 because fields moved. The review's `instance` addition keeps 2, since version 2 has never been released.
  - `blueprint/architecture.md`: the Snapshot and Project lines match the contract, plus one S03-outcome sentence each in "Discovery and sampling" and "Model and identity".
- **Scheduler.**
  - A dedicated thread, not `spawn_blocking`: one long-lived owner serializes scans by construction and keeps scanner state off async workers.
  - Refresh requests queue on `std::sync::mpsc`. Every request queued before a scan starts is answered by that scan; one arriving mid-scan waits for the next, so a reply always reflects a scan that started after the request.
  - After an overrun, the next scan waits a full interval from its end.
  - Panics are contained twice. A panic in a scan or in scanner construction (`Scanner::new` runs inside the guard) is a failed attempt, and the scan is rebuilt. A panic elsewhere in the loop publishes a final failure snapshot ("the scanner stopped unexpectedly") and logs it; later refreshes return `Stopped`.
  - The scan is injected as a closure, so tests can script failures, panics and slow scans deterministically. Production passes the real `Scanner`.
  - tokio's `sync` feature was added (no new crate). `SchedulerHandle::{latest, subscribe, refresh, refresh_within}` and `RefreshError` exist for S04/S08 and are tested. Outside tests they carry `#[cfg_attr(not(test), expect(dead_code))]`, which becomes a lint failure once S04 uses them.

Real-CLI script (shared setup, then `list`):

```bash
set -euo pipefail
T=$(mktemp -d); T=$(realpath "$T")
export GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1
g() { "$(xcode-select -p)/usr/bin/git" -c user.name=t -c user.email=t@example.invalid -c init.defaultBranch=main "$@"; }
for r in one/app two/app; do mkdir -p "$T/$r" && g -C "$T/$r" init -q && g -C "$T/$r" commit -q --allow-empty -m init; done
mkdir -p "$T/one/app/packages/web" && echo '{}' >"$T/one/app/package.json" && echo '{}' >"$T/one/app/packages/web/package.json"
g -C "$T/one/app" worktree add -q -b feature "$T/one/app wt é"
g -C "$T/two/app" checkout -q --detach
holders=(); pids=()
for d in "one/app/packages/web" "one/app wt é" "two/app"; do
  i=${#pids[@]}; mkfifo "$T/hold-$i"; sleep 600 >"$T/hold-$i" & holders+=($!)
  (cd "$T/$d" && exec "$OLDPWD/target/release/stackscan-fixture" --listen 127.0.0.1 --max-lifetime-secs 60 <"$T/hold-$i" >"$T/ready-$i") &
  pids+=($!)
done
for i in 0 1 2; do until [ -s "$T/ready-$i" ]; do sleep 0.05; done; done
target/release/stackscan list --json | jq --argjson pids "[$(IFS=,; echo "${pids[*]}")]" '
  .observation as $o | {schemaVersion, instance, revision, scanner,
   services: [$o.services[] | select(.process.identity.pid as $p | $pids | index($p))
              | {pid: .process.identity.pid, project, package, cpu: .process.metrics.cpu, memoryBytes: .process.metrics.memoryBytes}],
   projects: [$o.projects[] | select(.root | startswith("'"$T"'"))]}' | sed "s#$T#\$TMP#g"
target/release/stackscan list 2>/dev/null | grep -E "^PID|^($(IFS='|'; echo "${pids[*]}")) " | sed "s#$T#\$TMP#g"
kill "${holders[@]}"; wait "${pids[@]}" 2>/dev/null; rm -rf -- "$T"
```

Idle-sampling script: the same `set`, `T`, `export` and `g()` lines, then:

```bash
dirs=()
for r in 0 1 2 3 4; do
  mkdir -p "$T/r$r/main"; g -C "$T/r$r/main" init -q
  for p in 0 1 2; do mkdir -p "$T/r$r/main/pkg-$p"; echo '{}' >"$T/r$r/main/pkg-$p/package.json"; done
  g -C "$T/r$r/main" add . && g -C "$T/r$r/main" commit -q -m init && g -C "$T/r$r/main" worktree add -q -b feat "$T/r$r/linked"
  for w in main linked; do for p in 0 1 2; do dirs+=("$T/r$r/$w/pkg-$p"); done; done
done
holders=(); pids=()
for d in "${dirs[@]}"; do
  i=${#pids[@]}; mkfifo "$T/hold-$i"; sleep 600 >"$T/hold-$i" & holders+=($!)
  (cd "$d" && exec "$OLDPWD/target/release/stackscan-fixture" --listen 127.0.0.1 --max-lifetime-secs 120 <"$T/hold-$i" >"$T/ready-$i") &
  pids+=($!)
done
for i in "${!pids[@]}"; do until [ -s "$T/ready-$i" ]; do sleep 0.05; done; done
(exec /usr/bin/time -l target/release/stackscan serve --no-open --port 0 2>"$T/serve.err") &
timer=$!; sleep 0.5; serve=$(pgrep -P "$timer")
cpu() { ps -o time= -p "$serve" | awk -F: '{print $1 * 60 + $2}'; }
sleep 5; c0=$(cpu); r0=$(ps -o rss= -p "$serve")
sleep 60; c1=$(cpu); r1=$(ps -o rss= -p "$serve")
echo "serve: $(echo "$c1 - $c0" | bc) CPU-s in 60 s, RSS ${r0} -> ${r1} KiB"
kill -TERM "$serve"; wait "$timer" || true
grep -E "real|maximum resident|^stackscan" "$T/serve.err"
kill "${holders[@]}"; wait "${pids[@]}" 2>/dev/null; rm -rf -- "$T"
```

## Measurements

`cargo nextest run --workspace [--release] --no-capture -E 'binary_id(stackscan-core::scan_cost)'` runs 30 owned fixtures in 10 worktrees: 5 repositories, each with a main and a linked worktree, 3 packages per worktree. The machine had 55–56 TCP listeners visible in total. The test asserts:

- every fixture is attributed to its worktree and package, and there are 10 fixture projects;
- on the fixtures' sockets alone, exactly 2 git commands per worktree when cold and **0** over 20 warm scans (host services are excluded from exact counts because a real dev server may restart);
- the warm median stays under 300 ms and the cold scan under 1 s.

| Build   | cold scan (incl. git)     | warm min | warm median | warm max | median enumeration | median inspection + attribution + metrics |
| ------- | ------------------------- | -------- | ----------- | -------- | ------------------ | ----------------------------------------- |
| release | 104.9 ms, 28 git commands | 2.24 ms  | 2.36 ms     | 3.10 ms  | 1.94 ms            | 0.38 ms                                   |
| debug   | 89.8 ms, 26 git commands  | 4.71 ms  | 4.80 ms     | 5.13 ms  | 3.88 ms            | 0.93 ms                                   |

- **Scan cost.** A warm scan is under 0.2 % of the 3 s cadence; the cold scan is about 3.5 %.
- **Why release cold is slower than debug cold.** The cold scan is dominated by 26–28 sequential `git` spawns at 3–4 ms each, and the count varies with how many of this machine's own services sit in Git worktrees at that moment (20 are the fixtures'). The extra commands are read-only `rev-parse`/`symbolic-ref` runs with `GIT_OPTIONAL_LOCKS=0`; no real service was signalled.
- **One-shot `list --json`.** 65–80 ms (`lastAttemptDurationMs`), including scanner construction and git for the visible worktrees.
- **Idle overhead.** Resident `serve` (release, scheduler at 3 s) with the same 30 fixtures, from the idle-sampling script: the process itself used 0.12 CPU-s in 60 s (`ps` cputime), **0.2 % of one core**; including its reaped git children (`/usr/bin/time -l`), 0.56 CPU-s over 65.6 s, **about 0.85 % of one core**. Max RSS was 9.8 MB, and RSS stayed flat (8.8 → 9.2 MiB over the window). stderr held only the listening and stopped lines; `serve` exited 0 on SIGTERM. Most of the gap between the process's own CPU and the total is git children: 10 worktrees × 1 `symbolic-ref` per 15 s. Raising `HEAD_TTL` is the lever if idle cost matters more than branch freshness.

## Unverified or deferred

- **Filesystem-boundary stop.** Implemented as a device check (`st_dev`) but not fixture-tested: `/`, `/Users` and `/private` report the same device here, and mounting a volume in a test was out of scope.
- **Missing Command Line Tools.** The `gitUnavailable` path and the 60 s re-lookup are not exercised; the tools are installed here.
- **Real stalls.** A real git hang (stalled network filesystem) was not produced; the timeout, kill and helper-thread paths are covered by the runner's unit tests with `sleep`/`yes`. A stalled walk is unbounded by design (above).
- **Loop-level panic.** The outer guard (final failure snapshot when the loop itself panics) has no test; only scan and construction panics can be injected. A real enumeration failure is not reproducible (as in S02); failure handling is proven with scripted scans.
- **Over HTTP.** Snapshots are not served yet (S04). `serve` runs the scheduler; its behaviour is proven by app unit tests against the real scanner, not through an HTTP entry point. No real overrun occurred, so the overrun line was seen only in tests.
- **Same-second PID reuse.** Still undetected, as in S02. The CPU baseline is keyed by the same identity, so such a reuse would merge CPU history.
- **Non-Git monorepos.** Not grouped (each manifest directory is its own project); deferred to S06 profiles.
- **Submodule HEAD.** The test sees the branch `submodule add` checks out; detached submodules are covered by the general detached-HEAD test.
- **Paths with newlines.** Refused (`gitFailed`) by design, not tested.
- **Remote CI.** Has not run this tree. It needs the developer-directory `git` (present on macOS runners) in addition to S02's prerequisites.
