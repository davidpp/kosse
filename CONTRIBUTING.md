# Contributing

Kossé is built in vertical slices defined in [`blueprint/implementation-plan.md`](blueprint/implementation-plan.md). Each slice lands with tests through real entrypoints and a short evidence note in [`docs/evidence/`](docs/evidence/). AI-assisted contributions are welcome under the same bar: include the commands you ran and their results.

## Prerequisites

- macOS on Apple silicon (the only supported and tested v1 platform) with Xcode Command Line Tools (`xcode-select --install`) for the linker.
- Tests spawn short-lived owned listener processes on loopback, plus one on the `[::]` wildcard, and call `/usr/sbin/lsof` (ground truth) and `/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate`. The wildcard test is skipped when the application firewall is on, so it never triggers an "accept incoming connections" prompt.
- Tests never probe, signal or otherwise contact real services: every `kosse serve` a test starts runs with the debug-only `--probe-only=<PIDs>` and `--act-only=<PIDs>`, empty by default, so only the test's own fixtures are probed or can be stopped. Refusal tests name Kossé itself, launchd and a root process found with `ps`, and check with `ps` that nothing changed. The one exception to "owned ports only" is the default-port test: it binds `127.0.0.1:47831` to occupy it, or, if something already listens there, only connects to it (never sends data or signals).
- A Kossé you run yourself (menu-bar app, `serve`, `open`) may keep running during `bun run test`/`check`. It probes your project listeners, the tests' fixtures included, but every probe carries its sender's instance ID (`X-Kosse-Instance`, the snapshot's `instance`), and the probe tests count only their own server's requests.
- Attribution tests build temporary Git repositories with `git` from the active developer directory (`$(xcode-select -p)/usr/bin/git`, the same binary Kossé runs), ignoring global and system Git config and any inherited `GIT_*` variables.
- [mise](https://mise.jdx.dev), which pins every tool per repository in [`mise.toml`](mise.toml): Rust (also pinned in `rust-toolchain.toml`), Bun, Node (needed only by web test tooling), cargo-nextest, cargo-deny, zizmor, and cargo-about and cargo-auditable for `release:local`.

```sh
mise trust && mise install   # once per machine
bun install --frozen-lockfile  # also installs the repo-local Lefthook hook
bun run check
```

For the browser suite (`bun run test:e2e`), install its engines once per machine: `bunx playwright install webkit chromium chromium-headless-shell` (downloaded to Playwright's cache in `~/Library/Caches/ms-playwright`).

Installing needs network access (mise tool downloads, `bun install`, `cargo fetch`, and the advisory database for `bun run audit`). The built `kosse` binary embeds the web UI and needs neither Bun nor Node at runtime.

## Changes

- Keep a change to one concern; each commit should pass `bun run check`.
- Commit subjects follow lightweight [Conventional Commits](https://www.conventionalcommits.org/) (`feat(core): …`, `fix(api): …`, `docs: …`).
- Behaviour changes need tests that exercise the real path: owned fixture processes, the real HTTP server, a real browser. Tests must never signal a process they did not start.
- Fixture processes come from `kosse-fixtures` (`crates/fixtures`): `Fixture::spawn` launches the `kosse-fixture` binary, waits for its ready line, records PID, start time, cwd and endpoints, and cleans up through its own child handle after an identity check. A fixture also exits on stdin EOF (its owner died) and after `--max-lifetime-secs`. `kosse_fixtures::lsof` gives independent ground truth. `FixtureSpec::serve` picks what connections get (a non-HTTP banner by default, or HTTP 200 with a title, 404, 500, hang, huge body, a redirect to its own `/next`, self-signed HTTPS), `::record` keeps what each connection sent, `::args` sets an ignored command line (fake secrets, markup), `::ignore_term` catches `SIGTERM`, `::port` pins the port (also next to another fixture on the other loopback address), and `::supervise` runs a supervisor that restarts its child fixture on the same port (waiting while it is taken). Only processes in a project are probed automatically, so probe fixtures run in a project directory (`FixtureSpec::cwd`). Credential-shaped test values are assembled at run time so no secret-scanner-flagged literal enters the source. Run fixture tests with `cargo nextest run --workspace <filter>`: with `-p` alone they fail on a clean target, or run a stale fixture binary on a warm one.
- Tests never open a window or a browser on the desktop. Debug builds read three hooks for that (release builds do not have them): `KOSSE_TEST_WINDOW=headless` (invisible window, no Dock icon, prints `loaded <url>` per page load and then the open dashboard dialog's heading, `dialog "<heading>"` or `dialog null`), `headless-once` (also closes after the first load), `transparent` (a shown window at 1% opacity above other windows that lets every pointer event through, no Dock icon or activation: it renders and takes the control socket's clicks, for `test:window`) or `fail` (exercises the browser fallback); `KOSSE_TEST_OPENER=<program>` replaces `/usr/bin/open`; `KOSSE_TEST_TRAY=1` prints each rendered tray menu to stdout and takes `activate <item id>` lines on stdin, dispatched like a click. The tray icon itself is real and appears in the menu bar while such a test runs. `KOSSE_WINDOW_CONTROL=1` with `KOSSE_WINDOW_CONTROL_SOCKET=<path>` makes the window answer the agent control socket ([docs/agent-drive.md](docs/agent-drive.md)). Debug builds also show the preview identity (split-stem K tray and Dock icons, window title `Kossé · preview (<branch>)`).
- Every spawned `kosse` in tests gets `KOSSE_CONFIG_DIR`: `support::NO_CONFIG` (a directory that never exists) unless the test owns a temporary one. Tests never read or write the user's real profiles.
- If a change alters a contract in `blueprint/`, update the smallest relevant section in the same change and say why.
- Security-sensitive areas (HTTP guards, redaction, process signalling) get a test for the failure case, not only the happy path.

Security issues: see [SECURITY.md](SECURITY.md); please do not open public issues for them.

## Running the binary

`target/release/kosse serve [--port <n>] [--no-open]` serves the embedded UI and API on `127.0.0.1` (default port 47831) until SIGINT/SIGTERM. An occupied port exits 1 with a clear message; usage errors exit 2. Debug builds also accept hidden flags that release builds do not have: `--dev`, which `bun run dev` passes, admits the Vite authority `127.0.0.1:47833`; `--probe-only=<PID,…>` restricts automatic probing to those PIDs (empty: none), and `--act-only=<PID,…>` restricts stop/force to those PIDs and their direct children (others are `refused` `outsideTestScope`), both for tests (`--act-only` matches PID and the start time read at startup, and refuses PID 0 and 1). `bun run dev` passes neither: development is a real-user path, so its dashboard can stop the developer's own processes.

API (every route, the embedded UI included, refuses a `Host` other than `127.0.0.1:<port>` or `localhost:<port>`; API routes refuse requests a browser marks cross-origin):

| Route               | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/health`   | `Health`: name and version.                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `GET /api/session`  | `Session`: the per-instance action token (memory only, new on every start).                                                                                                                                                                                                                                                                                                                                                                                                       |
| `GET /api/snapshot` | The latest `Snapshot` of the single scanner.                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `GET /api/events`   | Server-Sent Events: a `snapshot` event with the current snapshot, then one per publication (newest only for slow readers; no replay). Ends when the server stops.                                                                                                                                                                                                                                                                                                                 |
| `POST /api/refresh` | `{}` → scans now and returns the `Snapshot`; at most one per second (`429` + `Retry-After`). Needs the same-origin `Origin`, `Content-Type: application/json` and `X-Kosse-Token: <token>`.                                                                                                                                                                                                                                                                                       |
| `POST /api/probe`   | `ProbeRequest` (`{identity, port}`) → probes that endpoint now ("try HTTP") and returns its `HttpProbe`, marked `requested`. Same requirements and limit as refresh; `409 staleIdentity` if the identity is not current, `422 notProbeable` for another user's or a non-loopback endpoint.                                                                                                                                                                                        |
| `POST /api/stop`    | `ActionRequest` (`{instance, identity, ports}`: every port the confirmation showed) → `SIGTERM` after a fresh check, then a bounded observation; returns an `ActionResult`. At most one stop/force per second that passes the guard and JSON checks, whatever its result (`429`).                                                                                                                                                                                                 |
| `POST /api/force`   | The same body → `SIGKILL`, only after a `stillRunning` stop of that identity in the last 60 s (each offer once), else `409` `forceNotOffered`. Same checks, results and limits as stop.                                                                                                                                                                                                                                                                                           |
| `POST /api/window`  | `WindowRequest` (`{route}`: `dashboard`, or `inspect`/`stop` with `pid` and `startedAtSecs`) → `204`: the menu-bar app shows its one dashboard window at that route and brings it forward. Same requirements as refresh; one per second. Other instances answer `409 notResident`.                                                                                                                                                                                                |
| `POST /api/profile` | `SaveProfileRequest` (`{root, profile}`; `profile: null` removes it) → saves the central profile of a project in the snapshot (or one already saved) and returns `SavedProfile`; the next snapshot applies it. Writes only Kossé's configuration file. Same requirements; its own limit of one per second. `404 unknownProject`, `422 invalidProfile` (naming the field), `409 configUnavailable` while the file is invalid or newer, `500 configWriteFailed` when writing fails. |
| `/api/preferences`  | `GET` → `Preferences` (`{allListeners}`; the defaults when there is no file, `409 configUnavailable` when it is invalid or newer). `POST` with the same body replaces them and returns them as stored, keeping the rest of the file. Writes only Kossé's configuration file. Same requirements as profile; its own limit of one per second. `400 invalidPayload` for an unknown field, `409`/`500` as for profile.                                                                |

Refusals are `ApiError` JSON (`hostNotAllowed` 421, `originNotAllowed`/`tokenRequired` 403, `unsupportedMediaType` 415, `payloadTooLarge` 413, `invalidPayload` 400, `staleIdentity` 409, `notProbeable` 422, `rateLimited` 429, `scannerBusy`/`scannerStopped` 503, `notResident` 409; for profiles `unknownProject` 404, `invalidProfile` 422, `configUnavailable` 409, `configWriteFailed` 500). A body over 16 KiB is `413` both when `Content-Length` declares it (refused before reading) and when a chunked body exceeds it while being read; a body within the limit that is not the expected JSON is `400`. Stop and force answer with an `ActionResult` body (after the guard and JSON checks above): `exited` (gone, ports free), `stillRunning` (force offered), `respawned` (a process with the same parent listens again), `endpointTaken` (another process listens) or `observationFailed` with `200`; `stale` (instance, identity or port set no longer current) or `forceNotOffered` with `409`; `refused` (Kossé itself, PID ≤ 1, another or unknown owner, unreadable, no start time, or `outsideTestScope` in debug builds with `--act-only`) or `permissionDenied` with `403`; `signalFailed` (nothing sent) or `internal` with `500`. `exited` lists in `shared` any process that already listened on the same port numbers before the signal. Only `exited` is success. Every response carries a strict CSP (`default-src 'self'`, no inline script), `nosniff`, `no-referrer` and `frame-ancestors 'none'`.

`serve` probes HTTP candidates on loopback (the current user's processes that run in a project, plus services the user's central profile declares `http`/`https`) with one bounded `GET <path>` per process and port every 15 s, where `<path>` is `/` until a `GET /` got an HTTP response and the profile's `probePath` (default `/`) after that (see `crates/app/src/prober.rs`); results appear on each endpoint's `http` from the next scan on.

`kosse list` prints Markdown (GFM) tables, the format agents read best and still readable in a terminal. The service table has one row per listening port with the columns `PROJECT` (name, plus `/<package path>` below the root), `BRANCH` (`detached@<commit>`, `?` when Git did not say, `-` outside Git), `SERVICE` (the configured service, `Name (id) [source]`, or `ambiguous: a, b`), `PORT`, `HTTP` (`<status> <url>` when it answered, otherwise the probe state: `pending`, `skipped: <reason>`, `timed out`, …), `PROCESS`, `PID.START` (the identity actions take) and `AGE`. A `## Configured, not observed` table (`PROJECT` root, `SERVICE`, `SOURCE`, `MATCH`) follows when configured services match no process, including saved profiles of projects that are not running. Process-, Git- and profile-derived cells pass `text::printable` and escape `|`, `` ` `` and `\`, so no name can add a row or column; unknowns are `-`, warnings go to stderr, and command lines appear only in `--json`, redacted. Filters: `--here` (the project of the current directory, resolved like attribution: a linked worktree is its own project; outside a project it exits 3), `--project <dir>` (a known root, or the project of that directory), `--port <n>`, `--service <id or name>`; they apply to `--json` too, which then holds only the matching services, their projects, the profiles in scope and the warnings that can concern them (an unknown-project process stays in the warnings under a project filter). `kosse list --json` prints the `Snapshot` contract (`web/src/generated/contracts.ts`): from a one-shot scan, revision 1 with no probes, so HTTP candidates read `pending`, and CPU `warmingUp` (one observation); `serve` samples and probes. When a verified Kossé answers on `--instance-port` (default 47831; `0` never asks), the read commands use that instance's snapshot instead (its revision and `intervalMs`, CPU sampled, probes done) unless its `schemaVersion` differs, which falls back to a one-shot scan with a note.

`kosse url <service|port> [--here | --project <dir>] [--json]` prints only `prober::open_url`'s `http(s)://localhost:<port>/` for the one endpoint that answered HTTP (any status; the profile's `probePath` is not appended). A name is a configured service ID or name; a number is a port. Several matching services (two worktrees), several answering ports, no match or no HTTP answer exit 1, with the endpoint's probe state on stderr. `--json` prints a `UrlAnswer` (`schemaVersion`, `url`, `port`, `identity`, `project`, `service`). Without a running instance nothing has been probed, so `url` needs `serve` or the menu-bar app. `kosse port <n> [--json]` prints `free`, qualified as "as far as this user can see" when other users' sockets are hidden (always, without administrator rights), or the service table's rows for that port; `--json` prints a `PortAnswer` (`state` `free`/`taken`, `otherUsersVisible`, `scannedAtMs`, the `services` and their `projects`). Exit codes of `list`, `url` and `port`: 0 answered, 1 negative answer (`notFound`, `ambiguous`, `noHttp`), 2 usage error (clap's message, also with `--json`), 3 refused (`notInProject`), 4 could not observe (`projectUnknown`, `scanFailed`, `configUnavailable`, `outputFailed`). A failure is one `kosse: …` line on stderr, or with `--json` a `CommandError` (`{error, message}`, shaped like `ApiError`); stdout carries only answers.

Project attribution runs `git` from the active developer directory (`xcode-select -p`); without Xcode or the Command Line Tools, services inside Git worktrees are reported with an `attributionUnavailable` warning instead of a project.

Project profiles (see [project metadata](blueprint/project-metadata.md)) are read from the central file `~/Library/Application Support/Kosse/config.json` (`KOSSE_CONFIG_DIR` overrides the directory) and from a `kosse.json` at a detected project root, re-checked at most once a second. `kosse config schema` prints the profile JSON Schema (the same as `docs/kosse.schema.json`), `kosse config path` the central file, and `kosse config move <old root> <new root>` re-attaches the profile of a moved project; profiles never follow a project by name.

`serve` runs the instance's single scanner loop (3 s cadence) on its own thread and logs scan failures, recoveries and overruns to stderr; nothing per request is logged.

The dashboard (`/`) lists projects as cards with their services; `/?inspect=<pid>.<startedAtSecs>` opens a service's Inspect sheet and `/?stop=<pid>.<startedAtSecs>` its Stop confirmation (a link never confirms it). It loads `GET /api/snapshot` once, then follows `GET /api/events`; listeners outside a project and other users' processes are hidden until "All listeners" is checked, a choice saved in Kossé's configuration (`/api/preferences`).

After `bun run build`:

- **Menu-bar app.** `target/release/kosse [--port <n>] [--no-open]` (no command) runs the same instance as `serve` plus a tray menu, and opens the dashboard window unless `--no-open`.
  - The menu: projects with their branch; each service as `name :port[, :port]` with Open (only for endpoints that answered HTTP), Inspect and Stop…; Open Dashboard; Quit Kossé.
  - Inspect and Stop… open `/?inspect=<pid>.<startedAtSecs>` and `/?stop=<pid>.<startedAtSecs>` in the app's one dashboard window. Stop… is the dashboard's own confirmation; the tray never signals anything.
  - The icon switches to its attention variant, with the reason as the menu's first line, only when discovery failed or no scan finished for three intervals; a failed probe never does.
  - Quit, SIGINT and SIGTERM stop Kossé only (server drained, scanner stopped, window closed), never observed services.
- **`kosse open [--port <n>]`** shows the dashboard window without a resident app. With the menu-bar app on the port, it asks that app to show its own window and exits. With `serve` or another `open` there, it opens the browser and says why. Otherwise it serves until its window closes, then exits, leaving nothing running.
- **One instance per port.** `kosse` and `kosse open` reuse an instance only if the socket on `127.0.0.1:<port>` belongs to the current user and it answers `GET /api/health` as `kosse` (with its `mode`) and `GET /api/snapshot` with an instance ID. There is no PID or lock file.
  - A second `kosse` asks the menu-bar app to show its window (`kosse: Kossé <version> is already running at <url>; showing its window`), or with `--no-open` only says where it runs. There is never a second window or scanner.
  - `kosse` exits 1 while a `kosse open` session holds the port (`… is a `kosse open` session, which stops when its window closes …`). With `serve` there it opens the browser instead.
  - Anything else on the port exits 1 (`… is in use by a process that is not Kossé …`, or `… is held by another user's process …`).
- **Dashboard window.** The internal `kosse window <url>` child process: WKWebView, loopback origin only, other links in the default browser, website data in memory only. It closes when its owner exits. If it cannot start, the default browser opens the dashboard and stderr says why (the tray menu too, until the next click); `open` then keeps serving until interrupted.

- **`kosse doctor [--port <n>] [--json]`** checks, without changing anything: platform, this executable and the `kosse` on `PATH`, the configuration file (parsed, permissions), who holds the port (free, a verified Kossé and its mode, or something else), `git` in the developer directory, `lsof`, login startup and whether this user is logged in at the screen. Exit 1 when a check fails, else 0 (warnings included).
- **`kosse startup enable|disable|status`** manages opt-in login startup: `enable` writes `~/Library/LaunchAgents/com.davidpp.kosse.plist` running this `kosse` with `--no-open` at each GUI login (`RunAtLoad`, `Aqua` sessions only, no `KeepAlive`, so Quit stays quit) and loads it with `launchctl bootstrap gui/<uid>`, which also starts it now; `disable` runs `launchctl bootout` (stopping a launchd-started Kossé, never observed services) and removes the plist; `status` only reads. Enable it from the installed binary: the agent names that path. Debug builds read `KOSSE_TEST_LAUNCHCTL=<program>` in place of `/bin/launchctl`; tests also point `HOME` at a temporary directory, so they never write a real agent or call the real `launchctl`.

## Local release

`bun run release:local [--url <archive URL>]` writes, in `artifacts/` (ignored by Git):

- `kosse-<version>-aarch64-apple-darwin.tar.gz`: the release `kosse` (`cargo auditable build --release --locked`, so `cargo audit bin` can check its embedded dependency list), `LICENSE`, `THIRD_PARTY_NOTICES.md`, `INSTALL.md` (from [`packaging/INSTALL.md`](packaging/INSTALL.md)) and `MANIFEST.json` (version, target, commit, whether the tree was dirty, `rustc` version, size and SHA-256 of each file). No AppleDouble files or extended attributes.
- the archive's `.sha256` file (`shasum -a 256 -c` format), checked before the script ends.
- `kosse.rb`: a Homebrew formula for exactly that archive, from [`packaging/homebrew/kosse.rb.tmpl`](packaging/homebrew/kosse.rb.tmpl). Unpublished: no tap exists and its URL is a placeholder unless `--url` names where the archive is hosted.

The notices come from cargo-about with [`about.toml`](about.toml), which restates the [`deny.toml`](deny.toml) license policy (keep the two identical; `cargo deny` enforces it), for the crates the release binary links on `aarch64-apple-darwin` (no dev or build dependencies), followed by the licenses Vite collects for the bundled JavaScript (`web/dist/.vite/license.md`). The script fails if the notices lose a license the policy singles out (MPL-2.0 option-ext, ISC ring, the Apache-2.0 tao and wry).

`install:local` checks the archive against its `.sha256`, its entries against a single top-level directory, every file against `MANIFEST.json`, and that the extracted `kosse --version` matches, then installs `<prefix>/bin/kosse` and `<prefix>/share/doc/kosse/` by rename (a running Kossé keeps its old file) and writes `<prefix>/share/kosse/install-record.json`: the files with their SHA-256 and the directories it created, rewritten after every step so an interrupted install can still be completed or removed. A file is install:local's only while it sits at a recorded path with the recorded SHA-256: an upgrade refuses to replace a file it did not install or one changed since (`--force` replaces changed recorded files). `uninstall:local` removes the recorded files that are unchanged, keeps (and keeps recording) changed ones unless `--force`, then removes the created directories if empty; it refuses a `kosse` it has no record of, a malformed record, and login startup that runs that binary (compared by file identity) or that it cannot read. `--purge` also removes the configuration file `kosse config path` names (and its lock), never anything else in that directory. Expected failures print one message and exit 1 (usage errors 2) after cleaning up their temporary directory.

## Releasing

Releases are cut from `main` by a tag; [`release.yml`](.github/workflows/release.yml) does the rest.

1. Bump `version` in the root `Cargo.toml` (`[workspace.package]`; `Cargo.lock` follows on the next build) and move CHANGELOG's Unreleased entries under `## X.Y.Z - YYYY-MM-DD`.
2. Merge to `main` with CI green.
3. Tag that commit and push the tag:

   ```sh
   git tag -a vX.Y.Z -m "Kossé X.Y.Z" && git push origin vX.Y.Z
   ```

On the tag, the workflow's macOS job:

- refuses a tag that does not name the Cargo version, or a version without its CHANGELOG section ([`scripts/release-notes.ts`](scripts/release-notes.ts), which also writes the release notes);
- runs `bun run check` and `bun run test:package` from a clean build (no caches);
- builds the published archive with `release:local --url` set to its release asset, so the attached `kosse.rb` installs exactly that file;
- checks the archive against its `.sha256`, that `MANIFEST.json` names the tagged commit and a clean tree, and that the binary reports the version;
- attests build provenance for the archive and `install.sh` (Sigstore, verifiable with `gh attestation verify <file> --repo davidpp/kosse`).

A separate job, the only one with write access, then publishes the GitHub Release with the CHANGELOG section as notes and these assets: `kosse-X.Y.Z-aarch64-apple-darwin.tar.gz`, its `.sha256`, `kosse.rb` and [`install.sh`](packaging/install.sh). Running the workflow manually (Actions → Release → Run workflow) is a dry run: the same build and checks, uploaded as a workflow artifact, nothing published.

Releases are not signed or notarized (no Apple Developer ID). The installer and README use `curl`, which sets no quarantine attribute, so the ad-hoc-signed binary runs.

## Package tests

`test:package` runs every installed `kosse` that scans under `sandbox-exec` with a profile that refuses outbound IP connections except to its own fixture's port: the release binary has no `--probe-only`, so this keeps its automatic probes away from the machine's real services (the suite checks that a second fixture outside the allowance gets a refused probe). It never enables login startup; `startup status` only reads. The menu-bar app it starts runs with `--no-open`, so only its real status item appears briefly.
